# External Python dependencies for saas_core/saas_website, beyond what Odoo
# 18 core's own requirements.txt already provides. Declared by name (no
# pins) in saas_core/__manifest__.py's external_dependencies.python; this
# file is what actually pins them for reproducible installs.
#
# Direct dependencies (the ones __manifest__.py names):
#   paramiko              - SSH transport to Docker/compute hosts
#   Jinja2                - config/manifest templating (odoo.conf, docker-compose.yml)
#   boto3                 - S3-compatible object storage (backups, registry)
#   google-cloud-storage  - GCS object storage backend
#
# Everything else below is their transitive closure, pinned for full
# reproducibility (a second `pip install -r` of this file always produces
# byte-identical versions — see docs/PRODUCTION-READINESS-PLAN.md, Phase A.1).
#
# IMPORTANT: these versions were resolved WITH Odoo 18's own requirements.txt
# (https://github.com/odoo/odoo/blob/18.0/requirements.txt) applied as a pip
# constraints file, for Python 3.12 (matching .github/workflows/ci.yml and
# devctl.sh's expected interpreter) — Jinja2, cryptography, idna, requests,
# urllib3, and python-dateutil are all also depended on by Odoo core itself,
# and installing this file's own unconstrained resolution would silently
# fight Odoo's pins (e.g. an unconstrained resolve pulled cryptography 50.x;
# Odoo 18 pins 42.0.8 for Python >= 3.12 specifically "for security fixes"
# alongside a matching pyopenssl version). Regenerate with:
#
#   curl -fsSL https://raw.githubusercontent.com/odoo/odoo/18.0/requirements.txt \
#     -o /tmp/odoo18-requirements.txt
#   python3.12 -m venv /tmp/reqpin-venv && . /tmp/reqpin-venv/bin/activate
#   pip install -c /tmp/odoo18-requirements.txt \
#     paramiko jinja2 boto3 google-cloud-storage
#   pip freeze > control-plane/requirements.txt   # then restore this header
