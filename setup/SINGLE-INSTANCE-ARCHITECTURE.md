# Current architecture: one instance, vertical resource scaling

Each tenant runs **one Odoo pod** (web/gevent container plus a smaller cron sidecar) and **one PostgreSQL instance**. There is no customer HA option, replica-tier catalog, replica-tier checkout, horizontal scaling method, autoscaling spec, or dedicated cron Deployment. The control-plane driver only provisions `spec.replicas: 1`, and the CRD rejects raising replicas on an existing instance. A legacy instance that still has `replicas > 1` keeps working: the operator runs one pod, removes the old cron Deployment and PDB, and reports a `ReplicasIgnored` warning condition.

A plan change updates CPU/RAM requests and limits of the existing workload, together with its Odoo worker configuration. Requests remain aligned with scheduling requirements; limits alone cannot guarantee capacity. Data storage can grow on the existing PVC, but cannot shrink. Plan changes use the existing billing/resize path and do not build a new image. Rolling updates can briefly run a replacement Odoo pod on the same node; this is deployment headroom, not an availability tier. Pod restarts, upgrades and node failures can interrupt service.

New Managed tenants share one data PVC between PostgreSQL and Odoo. Builds use only temporary pod storage and do not import/export build cache. Use one Longhorn storage replica under the current low-cost policy; provider snapshots and backup storage are still separate costs. Old volumes retain their existing layout and replication setting until explicitly migrated/reconfigured. See [storage migration and cache cleanup](STORAGE-COST-FIX.md).

Cron uses 25% of the web container's CPU/RAM limits, capped at 500m CPU and 512Mi RAM. Its requests are smaller as well. The web process uses `--max-cron-threads=0`; the cron sidecar uses `--no-http --workers=0` and the configured cron thread count. Disabling cron threads removes the sidecar. Both containers share the existing Odoo data directory and image; no extra PVC is allocated. The package's cost, capacity reservations, namespace quotas and Odoo usage metrics include cron. Rollout headroom includes both containers in the replacement pod. The cron sidecar has no readiness probe, so a cron restart never removes the pod from web traffic.

## Upgrade existing installations

1. Stop control-plane Odoo and every durable job worker. Back up the SaaS database and tenant data.
2. Identify any existing OdooInstance with `spec.replicas > 1` and patch it to `1` (recommended; the new operator otherwise runs one pod and warns). Wait until the one web pod is ready and the old cron Deployment is removed. This changes application count only; it does not move/delete storage.
3. For active tenants, apply the new package resource quota (including cron and replacement-pod headroom) before the operator rollout. Then apply the updated CRD and operator image `0.1.28`, following the storage rollout sequence. New operator/Helm deployments run one controller replica with a Recreate rollout, so old and new operators never reconcile at the same time.
4. Upgrade `saas_core` to `18.0.58.3.0`, `saas_billing` to `18.0.2.3.0` and `saas_website` to `18.0.6.2.0` together. The core pre-migration removes old tier view fields and cancels outstanding replica-scale jobs. Removed tier menus/actions/models are cleaned by Odoo's module upgrade. The frontend production bundle must also be updated. The billing migrations recompute stored margins to include cron and paused-tenant cost estimates.
5. Review any historical unpaid replica-tier invoices reported by the migration. Financial records are preserved; payment cannot activate the retired feature and future renewals no longer add tier charges. Resolve existing charges through the normal billing process.
6. Restart Odoo and all job workers. Confirm the portal has no tier selector or checkout, rejected multi-replica requests, working plan upgrades, retained backups, and unchanged database/attachment access.

The older multi-node cluster guide remains an infrastructure reference; it is not required for current tenant deployment. The single-node guide is the lower-cost starting point. Existing Kubernetes control-plane/storage redundancy is not changed automatically by a code update.

## Suspension and retained costs

Suspension scales the Odoo deployment (including cron and shell sidecars) and dedicated Managed PostgreSQL StatefulSet to zero. Legacy separate cron deployments are also stopped. Backup schedules and unfinished backup jobs are paused; init/restore/update jobs keep running to completion, and PostgreSQL is only stopped once they finish (the operator reports Progressing while it waits). PVCs, database credentials, and retained backups stay intact. StatefulSet claims explicitly use Retain on scale-down. CloudNativePG databases use `cnpg.io/hibernation=on`; normal reconciliation restores `off` on resume ([CloudNativePG hibernation documentation](https://cloudnative-pg.io/docs/devel/declarative_hibernation/)). External databases are left running because they may be shared. The operator retries suspension every 30 seconds to enforce it and catch late-created jobs.

On reactivation, the operator restores PostgreSQL first, resumes only jobs it paused once the database is ready, restores enabled backup schedules, and recreates the Odoo pod. Suspension interrupts running backup jobs; they restart on resume under their existing job retry policies. It does not delete partial backup artifacts or run a final backup. The retained source database and filestore remain the reactivation source.

The standard Managed tenant's rate-card estimate assigns zero CPU/RAM cost to stopped/suspended tenants but continues storage cost using at least the package's allocated data allowance. Parent estimates update when a child is suspended. This is an estimate, not provider metering: larger legacy claims, separate backup volumes, externally managed databases, registry images and object-store backups can cost more. Fixed-price VPS/node/control-plane charges do not fall when pods stop; suspension frees capacity for paying tenants. Existing volume minimum sizes remain billable, and Kubernetes cannot shrink PVCs.

No tenant PVC is deleted or copied automatically. Eliminating retained block-storage charges would require a separate verified cold-archive workflow: consistent PostgreSQL dump plus filestore archive, checksums and restore testing, durable archive metadata, delayed deletion only after verification, and a restore-based resume path. The current backup mechanism mounts the retained volume and is not a substitute for that lifecycle.

## Production availability status

The saved `state` continues to express lifecycle/billing intent. Customer project headers, lists, environment badges and fleet counts display observed availability instead. The project anchor is its Production tenant; staging/development have their own observations.

Online requires a live non-terminating Ready pod with the Odoo container ready, followed by a successful HTTP 200 response from the configured public `/web/health?db_server_status=1` endpoint confirming both `status: pass` and `db_server_status: true`. A stale CR Ready phase cannot prove a pod exists or serves traffic. During rolling updates the driver prefers a ready serving pod over an unready replacement. This checks basic Odoo and PostgreSQL connectivity, not every business workflow or customer database.

Missing/failed workloads and failed HTTP responses are Unavailable. Connection, DNS and TLS failures to the public URL are Unreachable from the platform. A cluster API failure means Unknown (observation failed), rather than asserting the tenant is down. Suspension/stop is shown as Stopping until the workload actually disappears; intent alone is not proof of shutdown. HTTP redirects and unrelated HTTP 200 pages do not prove health. Checks preserve TLS verification and never follow redirects.

Availability observation never starts/stops workloads or changes subscription/billing state. Public-URL failures cannot trigger an automatic restart. The existing lifecycle reconciler still uses workload health for its existing recovery policy; only its workload signal now comes from live pod readiness. A missing pod whose OdooInstance still exists (eviction, rescheduling) is left to the operator rather than recreated by the control plane, and a pod that is only terminating is not sent another stop.

Status polling and single-tenant detail requests refresh observations with a 20-second cache. A separate one-minute cron refreshes up to 50 observations, never-checked tenants first and then the oldest; it starts no new check after 30 seconds and commits after each tenant. Observations live in their own table (`saas.instance.runtime`), so status polls and the sweep never lock or conflict with the tenant record while a provisioning/restore job holds it. Fleet/list responses use cached observations rather than making a remote request per tenant. Observations older than 120 seconds become Unknown, on the server and browser, and the UI exposes the last check time. Large fleets may therefore show Unknown until a tenant is checked, instead of claiming stale availability. Individual remote calls have timeouts; the cron start budget is checked between tenants.

Upgrade `saas_core` and `saas_website` before serving the rebuilt frontend so the new observation fields and cron exist. Existing tenants start Unknown until observed. Validate the public health route, domain/TLS, outage classification, suspension, and restoration on the actual cluster; local regression tests do not certify production connectivity.
